# Upgrading to Version 4.6.0

> **Warning:** In development. 4.6.0 is the `develop` branch and has no tag yet. This guide is prepared in advance and the steps below will only work once v4.6.0 is tagged and published. The latest release is v4.4.1; 4.3.x remains the stable line recommended for production.

## Overview

Version 4.6.0 adds an opt-in change approval workflow: users with a change request permission file their zone edits for review instead of writing them, and reviewers approve or reject from a new **Change requests** page or through the API. Alongside it, secondary zones can be retrieved from their primary on demand, the SOA serial bump on unchanged saves can be turned off, and every setting is reachable from a Docker environment variable.

Nothing changes unless you turn the workflow on. See [What's New in 4.6.0](../whats-new/v4.6.0.md) for the full list.

## Database Schema Update

The 4.6.0 migration adds one table and four permissions:

| Change | Purpose |
|--------|---------|
| Table `zone_change_requests` | Stores filed change requests: the zone, requester, reason, the JSON action list with before/after rows, the reviewer, decision, the error when applying failed, and the zone file kept before an approved deletion |
| Permissions `zone_change_request_own`, `zone_change_request_others` | Request changes to owned zones, or to any zone |
| Permissions `zone_change_approve_own`, `zone_change_approve_others` | Review change requests for owned zones, or for any zone |

The permissions are not granted to any permission template automatically. Grant them in the template editor once `approval.enabled` is on - see [Change Requests](../user-guide/change-requests.md#permissions).

The scripts also repair databases that earlier updates left incomplete. Each step does nothing on a database that is already correct:

- PostgreSQL: the 4.1.0 update added permissions with fixed ids without moving the id sequence on, so later updates failed to add `user_enforce_mfa`, `zone_logs_view_own`, `zone_logs_view_others` and, on databases installed before 4.0.5, more of the 4.5.0 permissions. The 4.6.0 script resyncs the sequences and adds any of them that are missing, with the metadata and ownership view grants 4.5.0 gave alongside them. Grant the restored permissions in the template editor as needed.
- Databases upgraded from 4.0.0-4.0.4 straight to 4.1.0 or later never ran the 4.0.5 update: `records_zone_templ` gets its `id` primary key now, on MySQL and PostgreSQL the `zones` table also gets the `idx_zones_domain_id` and `idx_zones_owner` indexes fresh installs have had since 4.1.0.
- MySQL/MariaDB: `zone_change_requests` is created with the `utf8mb4_unicode_ci` collation fresh installs use, instead of the server default.

The SQLite 4.1.0, 4.2.0 and 4.3.0 update scripts rebuild tables. Run them once only: a second run drops the columns later updates added, and on an API backend database can empty the `zones` table.

The migration scripts are:

- `sql/poweradmin-mysql-update-to-4.6.0.sql`
- `sql/poweradmin-pgsql-update-to-4.6.0.sql`
- `sql/poweradmin-sqlite-update-to-4.6.0.sql`

Run the script even if you do not plan to use the workflow, so the schema matches the release.

## Upgrade Instructions

### Prerequisites

- Poweradmin v4.5.x
- PHP 8.2 or later
- Database backup

If you are upgrading from an older release, run the intermediate migration scripts first (4.3.0, then 4.4.0, then 4.5.0, then 4.6.0). Do not skip versions.

### Step 1: Backup Your Data

```bash
# MySQL/MariaDB
mysqldump -u username -p poweradmin_db > poweradmin_backup_$(date +%Y%m%d).sql

# PostgreSQL
pg_dump -h localhost -U username poweradmin_db > poweradmin_backup_$(date +%Y%m%d).sql

# SQLite
cp /path/to/poweradmin.db /path/to/poweradmin_backup_$(date +%Y%m%d).db
```

### Step 2: Download and Extract

```bash
cd /tmp
wget https://github.com/poweradmin/poweradmin/archive/refs/tags/v4.6.0.tar.gz
tar -xzf v4.6.0.tar.gz
rsync -av poweradmin-4.6.0/ /var/www/poweradmin/ --exclude=config/settings.php
```

### Step 3: Run Database Update

**MySQL/MariaDB:**

```bash
mysql -u username -p poweradmin_db < sql/poweradmin-mysql-update-to-4.6.0.sql
```

**PostgreSQL:**

```bash
psql -h localhost -U username -d poweradmin_db -f sql/poweradmin-pgsql-update-to-4.6.0.sql
```

**SQLite:**

```bash
sqlite3 /path/to/poweradmin.db < sql/poweradmin-sqlite-update-to-4.6.0.sql
```

### Step 4: Clear Cache and Restart

```bash
sudo systemctl restart php-fpm
# or
sudo systemctl restart apache2
```

## New Features

### Change Approval Workflow

Off by default. To turn it on:

```php
return [
    'approval' => [
        'enabled' => true,
        'require_review_for_all' => false,
    ],
    'notifications' => [
        'change_request_enabled' => false, // mail reviewers and requesters; needs mail.enabled
    ],
];
```

Then grant `zone_change_request_*` to the users who should file requests and `zone_change_approve_*` to the reviewers. Reviewers also need the edit permission for the zone; superusers review everything. With `require_review_for_all`, every change goes through review, editors and administrators included.

In Docker the variables are `PA_APPROVAL_ENABLED`, `PA_APPROVAL_REQUIRE_REVIEW_FOR_ALL` and `PA_NOTIFICATION_CHANGE_REQUEST`.

Two things to check before enabling it on a live installation:

- Dynamic DNS clients cannot file requests. An update from a user whose changes to the zone need review is refused (`!yours` from `dynamic_update.php`, `403` from the API endpoint). Keep an edit permission on DDNS accounts.
- API clients whose changes need review get `403` on the record write endpoints and have to use the change request endpoints instead.

See [Change Requests](../user-guide/change-requests.md).

### Other changes

- `dns.bump_serial_on_unchanged_save` (default `true`) lets an installation stop bumping the SOA serial on saves that change nothing. See [DNS Settings](../configuration/dns-settings.md#serial-bump-on-unchanged-saves).
- API v2 DNSSEC key changes (add, import, update, delete) now need view access to the zone as well as `zone_dnssec_manage_own`, as the web pages do. An API key whose user holds the DNSSEC permission without view access to the zone now gets `403`. See [API Endpoints](../api/endpoints.md#zone-metadata-and-dnssec).
- API backend mode on installs migrated from SQL mode: zone ids in the API v2 zone list, `GET /zones/{id}` and the internal zone list are now the canonical id, the same value every other zone endpoint takes (`canonical_id` stays and is equal to `id`). Before, the list reported the zones table row id, which could open a different zone. Clients that stored the old ids (for example Terraform state) see them change once.
- On the first request after the upgrade in API backend mode, stored API key zone restrictions are moved from row ids to canonical ids. A stored value that is no zone's row id but some zone's canonical id (a restriction saved in SQL mode before switching, or a deleted zone's id) then matches none, so the key keeps its restriction; the log names the key, and the zone has to be selected again on it. Until the move has run, a restricted key reaches no zone and new restrictions cannot be saved.
- In API backend mode a new zone no longer takes a zone id that a migrated zone, a group assignment or an API key restriction already uses; it gets the next free id instead. Before, it could take over a migrated zone's id and hide that zone.
- Group assignments made through the API before 4.6.0 hold the zone list's row id. The database consistency check lists those whose id now names no zone, so they can be assigned again.
- `dnssec.debug` and `PA_DNSSEC_DEBUG` are removed; they had no effect since the pdnsutil provider was dropped.
- Switching from the API backend back to the SQL backend is refused once the API backend has written zones to the database: zone ids written in API mode would point at other zones. The web pages show the error, the API answers `503`, and the command line and dynamic DNS updates stop. See [Migrating from SQL to API Backend](../configuration/powerdns-api.md#migrating-from-sql-to-api-backend).
- The SQL backend now stores the zone name whenever it writes a zone row, and the [Database Consistency Check](../maintenance/consistency-check.md) lists zones that still lack one, so a later switch to the API backend keeps every zone's owners.
- In API backend mode the automatic zone sync changes nothing when PowerDNS no longer lists more than half of the known zones, which usually means `pdns_api.url` points at the wrong server; the manual sync on the Forward Zones page still applies the changes.
- With `approval.enabled` on before the 4.6.0 update script has run, the Change requests entry and the pending counts are hidden and an error is logged, instead of every page failing. Filing a request still fails until the script has run.
- A `security.password_encryption` of `md5` or `md5salt` (removed in 4.3.0) now stops Poweradmin at startup with a message naming the setting. Before, every login of a bcrypt user failed. Set it to `bcrypt`, `argon2i` or `argon2id`; existing md5 password hashes still verify and are rehashed at the next login.

## Rollback

To roll back to v4.5.0:

1. Restore your database backup.
2. Restore your file backup.
3. Restart the web server.

The `zone_change_requests` table and the four permissions are harmless in 4.5.0 - they are simply unused. Pending change requests are not applied by the older version; decide them before rolling back or file them again afterwards.
